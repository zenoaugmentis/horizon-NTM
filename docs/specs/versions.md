# S01 · Эталон Minecraft 1.7.10: версии, установка и проверка

Задача: #14.
Первоначальная реализация: PR #109.
Повторная ручная проверка: Zeno, 2026-11-10.

Я повторно подготовил эталонное окружение Minecraft 1.7.10, вручную
установил Forge, проверил контрольные суммы основных файлов и выполнил
базовые проверки запуска клиента и сервера.

## 2. Расположение окружения

Для разработки я создал отдельный корневой каталог Minecraft:

`%USERPROFILE%\Documents\horizon-reference`

В Legacy Launcher я переключил именно корневой каталог игры.
Обычная игровая сборка осталась в прежнем месте.

В новом корне находятся собственные `versions`, `libraries`, `assets`
и игровые данные. Каталог расположен вне Git-репозитория.

Установленные профили:

- `1.7.10`
- `1.7.10-Forge10.13.4.1614-1.7.10`

Ваниль и Forge используют общий корневой каталог. Это отдельное
исследовательское окружение относительно моей обычной сборки,
но не две полностью независимые установки.

Ванильный сервер размещён отдельно:

`%USERPROFILE%\Documents\horizon-reference\server-vanilla`

Знак «—» означает, что размер отдельно не фиксировался.

Локальный Forge JAR называется
`forge-1.7.10-10.13.4.1614-1.7.10.jar`.
Его SHA-1 совпал с SHA-1 опубликованного артефакта universal.

После установки и запуска Forge я повторно проверил ванильный
`versions/1.7.10/1.7.10.jar`. Его SHA-1 остался прежним.

SHA-1 используется для сопоставления файлов с опубликованными
метаданными. Совпадение отдельного JAR не является полной проверкой
всего окружения запуска.

## 4. Подготовка клиента и Forge

### Ванильный клиент

Я установил обычную версию 1.7.10 через Legacy Launcher
в новый корневой каталог и успешно запустил игру.

Клиентский JAR совпал с официальным артефактом по размеру и SHA-1.

### Ручная установка Forge

Я скачал установщик по прямой ссылке:

https://maven.minecraftforge.net/net/minecraftforge/forge/1.7.10-10.13.4.1614-1.7.10/forge-1.7.10-10.13.4.1614-1.7.10-installer.jar

Затем:

1. Сверил его SHA-1 с опубликованным файлом `.sha1`.
2. Запустил установщик через Java 8u51.
3. Выбрал `Install client`.
4. Указал корневой каталог `horizon-reference`.
5. Проверил SHA-1 установленного Forge JAR.
6. В лаунчере выбрал установленный профиль Forge и Java 8.

Автоматическую установку Forge средствами лаунчера я не использовал.

### Проверка Forge-клиента

В журнале запуска зафиксированы:

```text
Forge Mod Loader version 7.99.40.1614 for Minecraft 1.7.10 loading
Java is Java HotSpot(TM) 64-Bit Server VM, version 1.8.0_51
MinecraftForge v10.13.4.1614 Initialized
Forge Mod Loader has successfully loaded 3 mods
```

Я создал новый мир, поставил и сломал блок и вышел в главное меню.
Проверка прошла успешно. Записей уровня ERROR/FATAL в проверенном
журнале после теста мира не обнаружено.

Диагностическая строка `THIS IS NOT A ERROR` не является
сообщением уровня ERROR.

В первоначальном фрагменте журнала присутствовала строка стека
`ForgeVersion$1.run`. Полный контекст этой записи не установлен;
она не помешала загрузке игры и выполнению проверки мира.

## 5. Подготовка ванильного сервера

Я скачал сервер напрямую из хранилища Mojang:

https://launcher.mojang.com/v1/objects/952438ac4e01b4d115c5fc38f891710c4941df29/server.jar

После скачивания проверил размер и SHA-1.

Для журналирования я использовал конфиг Mojang:

https://launcher.mojang.com/v1/objects/4bb89a97a66f350bc9f73b3ca8509632682aea2e/log4j2_17-111.xml

Его SHA-1 также проверен.

Инструкция Mojang по защите старых версий:

https://www.minecraft.net/en-us/article/important-message--security-vulnerability-java-edition

Начальные параметры `server.properties`:

```properties
server-ip=127.0.0.1
server-port=25565
online-mode=true
motd=Horizon S01 vanilla reference
```

Сервер слушал только локальный адрес `127.0.0.1`.

Первый запуск создал `eula.txt` и остановился с требованием
принять условия. После ознакомления с EULA я вручную изменил
значение на `eula=true` и повторил запуск.

### Команды воспроизведения

Команды PowerShell приведены по одной строке.
Путь к Java необходимо адаптировать к своей установке.

Переход в каталог сервера:

```powershell
Set-Location -LiteralPath "$env:USERPROFILE\Documents\horizon-reference\server-vanilla"
```

Запуск:

```powershell
& "$env:APPDATA\.tlauncher\legacy\Minecraft\jre\jre-legacy\windows-x64\jre-legacy\bin\java.exe" "-Dlog4j.configurationFile=log4j2_17-111.xml" -Xms512M -Xmx1G -jar ".\minecraft_server.1.7.10.jar" nogui
```

Остановка из консоли сервера:

```text
stop
```

### Известная ошибка остановки

В обоих запусках после сообщений сохранения появлялись:

```text
Attempted to append to non-started appender File
Unable to write to stream logs/latest.log for appender File
java.io.IOException: Stream Closed
Attempted to append to non-started appender ServerGuiConsole
Exception in thread "Server Shutdown Thread"
```

Подтверждённый факт: ошибка возникает при записи журнала
в процессе завершения сервера.

Предположение: поток завершения продолжает журналирование
после закрытия appender. Точная причина не установлена.

Я фиксирую запуск и повторную загрузку мира как успешные,
а остановку — как завершение с исключением журналирования.
Полностью безошибочное завершение не подтверждено.

Повторная загрузка мира не заменяет проверку целостности
каждого сохранённого чанка.

## 7. Особенности JSON профиля Legacy Launcher

Я дополнительно сравнил локальный JSON ванильного профиля
с отдельно скачанным официальным JSON Mojang.

| Файл | SHA-1 |
|---|---|
| Официальный JSON Mojang | `ed5d8789ed29872ea2ef1c348302b0c55e3f3468` |
| Локальный JSON профиля Legacy Launcher | `489c58b29fa6c01c1dd5d1e7b069842d35f38871` |

При сравнении разобранных JSON различия обнаружены в полях:

- `assetIndex`
- `complianceLevel`
- `downloads`
- `family`
- `libraries`
- `logging`
- `releaseTime`
- `time`
- `tlauncherVersion`

Использованный способ сравнения может также учитывать порядок
вложенных свойств. Подробное объяснение каждого отличия
не входит в выполненную базовую проверку S01.

В показанных полях локального ванильного профиля указаны:

- главный класс `net.minecraft.client.main.Main`;
- Java component `jre-legacy`, major version `8`;
- ожидаемый SHA-1 индекса ассетов.

Различие JSON не означает изменения клиентского JAR:
хеш самого JAR совпал с официальным.

Локальный JSON не заменялся официальным файлом.

## 8. Программа проверки файлов

В PR #109 добавлены:

- `tools/verify_vanilla_1710.py`;
- `tests/test_verify_vanilla_1710.py`.

Программа проверяет SHA-1 и размеры следующих компонентов:

- клиентский JAR;
- JSON версии;
- индекс ассетов;
- серверный JAR;
- Forge universal JAR.

Она не запускает игру, не проверяет миры и не подтверждает
полную чистоту библиотек или параметров запуска.

Требуется Python 3.10 или новее.

Пример запуска из корня репозитория:

```powershell
python tools/verify_vanilla_1710.py --game-dir "$env:USERPROFILE\Documents\horizon-reference" --server-jar "$env:USERPROFILE\Documents\horizon-reference\server-vanilla\minecraft_server.1.7.10.jar" --forge-universal "$env:USERPROFILE\Documents\horizon-reference\libraries\net\minecraftforge\forge\1.7.10-10.13.4.1614-1.7.10\forge-1.7.10-10.13.4.1614-1.7.10.jar" --report ".local/s01-report.json"
```

Программа ожидает фиксированную структуру каталогов.

В моей установке локальный JSON профиля отличается от официального,
поэтому его проверка существующим скриптом должна дать MISMATCH.
Этот результат нельзя автоматически считать допустимым или
подменять PASS. Его следует рассматривать отдельно от результата
проверки клиентского JAR.

В описанной ручной проверке я использовал PowerShell.
Запуск Python-проверки на моей установке и получение JSON-отчёта
в рамках этой сессии не выполнялись.

Команда тестирования программы:

```powershell
python -m unittest discover -s tests -p "test_verify_vanilla_1710.py" -v
```

Тесты используют искусственные файлы и проверяют саму программу.
Они не заменяют ручные результаты запуска Minecraft.
