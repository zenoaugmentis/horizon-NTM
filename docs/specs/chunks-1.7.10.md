# S03 · Чанки Minecraft 1.7.10: собственная спецификация и эталонные опыты

Проверку на Windows выполнил Zeno. Материалы собраны 2026-11-13.
Задача: https://github.com/zenoaugmentis/horizon-NTM/issues/16.
Зависимости: S01 — версии; S02 — ID и metadata.

Документ составлен по ручным опытам и присланным результатам, до принятия решений
о замене реализации S03. Это спецификация хранения и результатов проверки,
а не заявление о готовности движка или полной совместимости с Forge.

## 1. Статус утверждений

- **Эталон**: наблюдение в сохранении Minecraft, результат которого Zeno сообщил
  после локального запуска. Файлы миров в комплект не передавались.
- **Синтетика**: собственные заданные значения, не созданные игровой модификацией.
- **Контракт**: правило для будущего читателя/писателя Horizon. Оно не обязательно
  повторяет все побочные эффекты vanilla.
- **Не проверено**: нельзя выводить из успеха остальных проверок.

## 3. Координаты и геометрия

Контракт: мир имеет допустимые block Y `0..255`, секция 16×16×16, Y секции `0..15`.
Игровой опыт подтвердил принятие блока на 255 и отказ на 256; нижняя граница
отдельной командой не проверялась. Чанк имеет 16×16 столбцов, region — 32×32 чанка.

Для мировых координат блока:

```text
cx = floor(x / 16)        cz = floor(z / 16)
rx = floor(cx / 32)       rz = floor(cz / 32)
slot = (cx & 31) + 32 * (cz & 31)
sectionY = floor(y / 16)
localX = x & 15           localZ = z & 15       localY = y & 15
i = localY * 256 + localZ * 16 + localX
column = localZ * 16 + localX
```

Применять floor, не усечение к нулю. В Python используйте `//`, в других языках
явно проверьте отрицательные координаты. Пример: `-45.3` относится к блоку `-46`.
F3 XYZ — координаты игрока; для эталонных маркеров использованы точные `/setblock`.

Эталон точки `(-46,67,253)`: чанк `(-3,15)`, region `r.-1.0.mca`, slot 509,
секция 4, локальные `(2,3,13)`, индекс 978.
Проверены приращения: X+1 → 979; Y+1 → 1234; Z+1 → 994.
Индекс столбца 210 использован при HeightMap-опытах; независимая проверка
раскладки Biomes игровыми маркерами не выполнена.

Каталоги: обычный мир `region/`, Незер `DIM-1/region/`, Энд `DIM1/region/`.
Проверены именно эти каталоги. Политика именования измерений модов отдельно не проверена.

## 4. Контейнер Anvil

Имя `r.<rx>.<rz>.mca`. Сектор — 4096 байт, два первых сектора — заголовок.
Первые 4096 байт: 1024 big-endian u32 location. В записи старшие 24 бита —
начальный сектор, младшие 8 — число секторов. Location=0 означает отсутствие записи.
Вторые 4096 байт: 1024 timestamp по четыре байта. Перепись сохранила эти байты
без изменений; интерпретация времени как эпохи/знаковости экспериментом не проверялась.

Запись чанка: длина u32 BE, байт сжатия, сжатое NBT. Длина включает байт сжатия,
но не первые четыре байта. Проверка вместимости: `length + 4 <= sectors * 4096`.
У занятого чанка начало >=2, count>0; выделенные интервалы не должны пересекаться
и выходить за файл. Контракт записи ограничивает count значением 255;
граница максимального размера настоящим большим чанком не проверена.

Поддерживаемые варианты инструмента: 1=gzip, 2=zlib. Первый реальный образец:
slot 128, offset 8192, length 2675, payload 2674 байта, zlib `78 9C`,
несжатое NBT 52994 байта. Тип 2 подтверждён образцом; общее распределение
сжатий историческими выводами не зафиксировано. Gzip покрыт новой локальной
синтетической проверкой. Типы 3/4 и внешние `.mcc` не являются входом нашего
legacy-контракта; это правило инструмента, а не опыт с такими vanilla-файлами.

## 5. NBT и сохранность

Big-endian; в реальном первом образце корень — Compound (10) с пустым именем,
внутри `Level: Compound`. Модель читателя хранит тип каждого тега, порядок
Compound, тип элементов List даже при нулевой длине и дополнительные теги.
В первом vanilla-чанке Entities и TileEntities — пустые `List<End>`, поэтому
нельзя требовать `List<Compound>` для каждого пустого списка.

Контракт типов: End=0, Byte=1, Short=2, Int=3, Long=4, Float=5, Double=6,
ByteArray=7, String=8, List=9, Compound=10, IntArray=11. LongArray (12)
не входит в этот legacy-контракт. Поддержка типов парсером сама по себе
не доказывает, что каждый из них встретился в игровых образцах.

Строки писателя — Java modified UTF-8 по 16-битным единицам UTF-16:
NUL как C0 80, символ вне BMP как пара трёхбайтовых суррогатов.
Синтетический опыт содержит NUL и U+1F600. Читатель инспекции сохраняет
суррогатные единицы; сравнение выполняется по UTF-16 с surrogatepass,
а не обычным равенством Python-строк. Это не Unicode normalization.

**Ограничение текущего исследовательского кода:** читатель строк использует
упрощённое декодирование UTF-8 с заменой C0 80. Это не строгая полная реализация
Java DataInput modified UTF-8 для всех нестандартных/повреждённых последовательностей.
Float/Double проходят через Python float: все битовые варианты NaN
универсально без потерь не гарантируются. В частности signaling Float NaN
`7f800001` на проверенной локальной платформе становится `7fc00001`.
Глубина парсера ограничена 100, состояние raw/pos глобальное, параллельное
использование не предусмотрено. Это инструменты для доверенных локальных эталонов.

Для исследованных 2668 чанков byte-exact NBT подтверждён. Универсальное
обещание «любой NBT всегда byte-exact» из этого не следует. В будущем
производственный codec обязан либо сохранять исходные биты нетронутых
скаляров, либо явно ограничить контракт. Регион целиком byte-exact не требуется:
сжатие и размещение секторов при переписи меняются.

## 7. Секции и блоки

| Тег | Тип | Длина |
|---|---|---:|
| Y | Byte | Номер 0..15 |
| Blocks | ByteArray | 4096 |
| Add | ByteArray, если присутствует | 2048 |
| Data | ByteArray | 2048 |
| BlockLight | ByteArray | 2048 |
| SkyLight | ByteArray в исследованных секциях | 2048 |

Четырёхбитное значение для i: `(array[i//2] >> (4*(i%2))) & 15`.
ID = `Blocks[i] | (AddNibble(i) << 8)`, при отсутствии Add старшие биты ID=0.
Metadata = DataNibble(i). Свет читается такими же нибблами.

Игровые маркеры в одной секции:

| Координата | Индекс | ID/meta |
|---|---:|---|
| -46,67,253 | 978 | 35/14, красная шерсть |
| -45,67,253 | 979 | 35/11, синяя шерсть |
| -46,68,253 | 1234 | 35/5, зелёная шерсть |
| -46,67,254 | 994 | 35/4, жёлтая шерсть |

Общий Data[489]=BE hex. Проверено и обратное направление: собственная
запись 35/14 → появление шерсти в игре; замена землёй в игре → чтение 3/0.

Add во всех 2836 секциях Forge-копии отсутствовал. Только синтетически проверены
ID 0..4095 в чётной/нечётной позиции, границы диапазона и независимые векторы:
255/256/1204/4095 → Blocks `FF 00 B4 FF`, Add `10 F4`.
Отдельный тест проверяет Add внутри NBT и дополнительные теги корня/Level/секции.
Реальный модовый блок >255, NTM, unknown ID после удаления мода — **не проверены**.

Контракт читателя: отклонять неверные размеры, повтор Y и неверный тип Y;
набор исторических полных проходов не был всеобъемлющим валидатором этих ошибок.
При записи без потерь сохранять существующий Add, даже если он стал нулевым.
Это проектное требование; его появление/удаление самой игрой здесь не проверялось.

## 8. Пустые и отсутствующие секции

Первый чанк обычного мира содержал только секции 0..4.
В целевом чанке после установки маркера на Y=255 появились секции 0..4 и 15.
После последующих опытов игра сохранила все 0..15. После удаления высотных
маркеров все секции 5..15 содержали ровно 0 не-air ID (проверены Blocks и Add).

Следовательно, существование секции не означает наличие не-air блоков.
Отсутствующая секция и присутствующая пустая секция — разные представления:
вторую нельзя автоматически выбрасывать в режиме без потерь. В пустой секции
могут оставаться значимые массивы света и неизвестные теги.

Контракт: отсутствие секции даёт ID/meta 0/0. Значения света отсутствующей
секции должны определяться политикой измерения и освещения; безусловное
SkyLight=15 везде ниже рельефа этим опытом не подтверждено.
Создание отсутствующей секции нашим писателем и её освещение не проверены:
высокую секцию создавала игра. Дополнительные секции не следует приписывать
конкретному алгоритму без отдельной проверки исходников/инструментирования.

## 9. Свет

Эталон источника `(-46,100,253)`:

| Точка | ID | BlockLight | SkyLight |
|---|---:|---:|---:|
| Источник glowstone | 89 | 15 | 14 |
| X+1 | 0 | 14 | 15 |
| X+2 | 0 | 13 | 15 |
| Y+1 | 0 | 14 | 15 |
| Z+1 | 0 | 14 | 15 |

После удаления источника во всех пяти точках: ID=0, BlockLight=0, SkyLight=15.
Подтверждены раздельность массивов и чтение наблюдаемого затухания.
Причина SkyLight=14 внутри источника отдельно не устанавливалась.

В Незере все 5770, в Энде все 716 исследованных секций имели
SkyLight[2048] из нулей. Отсутствие неба не означает отсутствие тега.
Отсутствующий SkyLight ни одним реальным образцом не подтверждён.
Читатель может разрешить отсутствие как явно описанную политику совместимости,
но это не следует обозначать как установленное поведение vanilla.
В Forge-копии: 2079 нулевых и 757 ненулевых SkyLight-массивов.

Слой хранения сохраняет свет как есть. Само изменение Blocks не является
доказательством пересчёта света: эта операция принадлежит отдельной системе.
Световые флаги не заменяют проверки содержимого массивов.

## 10. HeightMap и предельный Y

Для столбца x=-46,z=253, column=210:

| Шаг | HeightMap |
|---|---:|
| До верхних маркеров | 69 |
| Установлен блок на Y=255 | 69 |
| Добавлен блок на Y=254 | 255 |
| Удалён блок на Y=255 | 255 |
| Удалён блок на Y=254 | 69 |

Блок на Y=255 подтверждён чтением ID 35/meta14 в секции 15 по индексу 4050.
Поэтому исходное ожидание HeightMap=256 не подтвердилось.
Результат не позволяет объявить общее правило «HeightMap всегда highest+1»
для предельного Y, ошибку игры или причину особенности. Для блока на 254
наблюдение согласуется с +1. Слой хранения сохраняет прочитанный HeightMap
без самовольной коррекции. Общее определение непрозрачности и точный алгоритм
обновления/пересчёта остаются для W10 и дополнительной сверки исходников.

## 11. Biomes и TileTicks

Biomes хранятся как беззнаковые байтовые значения. В первом образце
наблюдались 4 и 5, всего 256 столбцов. Sentinel 255, отсутствие Biomes,
сопоставление названия биома числу и порядок столбцов через игровой маркер
этими опытами не подтверждены. Контракт может назначить 255 значением
«не вычислен», но это отдельное правило, которое ещё требует источника/опыта.

TileTicks найдены в 16 Forge-чанках, всего 45 записей. Во всех каждой записи
имеются i,p,t,x,y,z, все типа Int(3). Следовательно, i как строка не соответствует
этим образцам. Отсутствие TileTicks необходимо поддерживать.
Поля p/t действительно существуют, но смысл приоритета, задержки, знаковость
значений и обработка отсутствующего p отдельным опытом не установлены.
Отсутствующее p=0 может быть политикой совместимости, а не доказанным фактом.

## 12. Требования к будущему хранению Horizon

1. Legacy-путь отделён от современной палитровой структуры чанка; преобразование
   числовых ID/meta следует S02. Реализация Rust в этих опытах не участвовала.
2. Неизменённые данные сохраняются по типам и значениям; байтовые гарантии codec
   должны быть сформулированы с учётом строк, Float/Double, порядка и пустых List.
3. Изменение одного блока сохраняет соседний ниббл, Add и дополнительные теги.
4. HeightMap, свет, TileTicks и TileEntities не исправляются скрытно слоем хранения.
5. Ошибочные координаты и индексы отклоняются до записи, а не маскируются.
6. Новый region проверяется повторным чтением; для будущего производственного
   писателя требуется атомарная замена/восстановление после сбоя, здесь это не тестировалось.
7. Заголовки, сжатие и выделение секторов проверяются отдельно от NBT.
