# S02 · Контракт блоков Minecraft 1.7.10 и модовых реестров

Задача: #15.
Зависимость: S01, `docs/specs/versions.md`.
Проверку выполнил: Zeno.
Дата: 2026-11-11.

Я проверил структуру реестра настоящего Forge-мира, сохранение ID
и metadata блока, преобразование реестра через Python-модель
и автоматические тесты контракта.

В документе разделены факты о проверенном сохранении,
правила Python-модели и проектные решения Horizon.
Успех тестов модели не означает, что контракт уже реализован
в Rust или полностью воспроизводит Forge.

## 1. Назначение

Контракт определяет:

- представление числового ID блока и metadata;
- связь имён блоков и предметов с числовыми ID;
- загрузку и сохранение реестра конкретного мира;
- обработку неизвестных ID и отсутствующих модов;
- границу между legacy-данными и внутренними состояниями Horizon.

Основные файлы:

- `docs/contracts/blocks.md` — контракт и результаты проверки;
- `tools/legacy_blocks.py` — исполняемая Python-модель;
- `tests/test_legacy_blocks.py` — тесты модели.

Реализация типов и поведения в Rust относится к W01/W02.
Формат секций мира подробно рассматривается в S03,
предметы и ItemStack — в S08, модовый API — в S10.

## 2. Модель ID и metadata

| Понятие | Представление |
|---|---|
| Legacy block ID | Целое число `0..=4095`, 12 бит |
| Legacy metadata | Целое число `0..=15`, 4 бита |
| Legacy item ID в модели | Целое число `0..=31999` |
| Имя зарегистрированного объекта | Строка с namespace: `modid:name` |

Пара ID/meta описывает legacy-состояние блока.
Она не заменяет полную модель предмета, TileEntity или поведения блока.

Концептуальное представление:

```rust
pub struct LegacyBlock {
    id: u16,
    meta: u8,
}
```

Создание значения должно проверять диапазоны.
Недопустимые значения не должны молча обрезаться конструктором.

### Упаковка пары

Для внутреннего ключа Python-модели используется:

```text
packed = (id << 4) | meta
id = packed >> 4
meta = packed & 15
```

Диапазон packed: `0..=65535`.

Все 65 536 комбинаций допустимых id/meta имеют уникальное значение packed.
Это математическое представление пары, а не отдельное поле Anvil.

### Представление в секции Anvil

Для блока с индексом i:

```text
id = (Blocks[i] & 255) | (AddNibble[i] << 8)
meta = DataNibble[i]
```

Если массив Add отсутствует, старшие биты ID считаются нулевыми.

Массивы Add и Data хранят по два четырёхбитных значения в байте:

- чётный индекс — младшие четыре бита;
- нечётный индекс — старшие четыре бита.

Индекс блока внутри секции:

```text
i = (local_y << 8) | (local_z << 4) | local_x
```

При преобразовании данных нельзя терять неизвестные ID
или исходные значения metadata только потому,
что соответствующее поведение блока ещё не реализовано.

## 3. Имена и реестр мира

Числовой ID модового объекта не считается глобальным постоянным
идентификатором между разными мирами и наборами модов.

Реестр связывает:

```text
вид объекта + namespaced name ↔ числовой ID
```

Блоки и предметы имеют отдельные таблицы имён.
В просмотренном коде FML их распределение координируется
общей картой занятости ID.

Для соответствующего ItemBlock имя и числовой ID
совпадают с именем и ID блока.

Наличие блока само по себе не означает наличие ItemBlock.

### Структура FML в level.dat

В проверенном сохранении корень NBT содержит:

```text
FML
Forge
Data
```

Раздел FML содержит:

| Поле | Назначение |
|---|---|
| `ItemData` | Записи имён и числовых ID |
| `BlockedItemIds` | ID, заблокированные от повторной выдачи |
| `BlockAliases` | Алиасы имён блоков |
| `ItemAliases` | Алиасы имён предметов |
| `BlockSubstitutions` | Записи подмен блоков |
| `ItemSubstitutions` | Записи подмен предметов |
| `ModList` | Идентификаторы и версии модов |

Запись блока в ItemData:

```text
K = "\u0001" + namespaced_name
V = block_id
```

Запись предмета:

```text
K = "\u0002" + namespaced_name
V = item_id
```

Префиксы являются управляющими символами,
а не буквальными шестью символами обратной косой черты и `u0001`.

## 4. Правила Python-модели реестра

Далее описано поведение `tools/legacy_blocks.py`.
Оно является проверяемым контрактом проекта.
Полная эквивалентность всем сценариям Forge не заявляется.

### Регистрация

- Блок получает свободный подсказанный ID в диапазоне `0..=4095`.
- Если подсказка непригодна, поиск начинается с 0.
- Обычный предмет получает свободный подсказанный ID
  в диапазоне `0..=31999`.
- Если подсказка непригодна, поиск для предмета начинается с 4096.
- Занятые и заблокированные ID не выдаются повторно.
- Регистрация блока с `item_block=True` создаёт также запись
  предмета с тем же именем и ID.
- Регистрация с `item_block=False` не создаёт предмет.
- После freeze публичная регистрация запрещена.

Число 4096 — начало поиска свободного ID обычного предмета
при отсутствии подходящей подсказки, а не нижняя граница
всех существующих предметов.

Сценарии «первый модовый блок получает 165» и
«первый модовый предмет получает 4096» проверены на тестовом
реестре Python-модели с заданным ванильным наполнением.
Это не отдельный эксперимент с регистрацией настоящего мода в Forge.

### Загрузка реестра мира

Модель:

1. Читает blocked ID, алиасы и substitutions.
2. Загружает записи блоков, затем предметов.
3. Использует ID, записанные в мире.
4. Помечает отсутствующие в наборе зарегистрированных объектов
   имена как missing.
5. Сохраняет missing-записи и резервирует их ID.
6. Добавляет новые объекты, не занимая ID сохранённых записей.

Старый формат `ModItemData` без `ItemData` модель отклоняет.

### Сохранение

Модель формирует FML с таблицами имён и ID,
blocked ID, алиасами, substitutions и ModList.

Порядок записей ItemData может изменяться.
Для round-trip сравнивается содержимое отображения имя/ID,
а не побайтовое равенство NBT.

Сохранение произвольных неизвестных расширений раздела FML
текущей моделью не гарантируется.

### Клиентская карта

Метод from_handshake() моделирует принятие карты сервера.
В итоговом реестре остаются только записи, переданные сервером.

Это тест модели карты, а не реализация или проверка настоящего
сетевого handshake Forge. Сетевой формат относится к S04/S07.

## 5. Unknown и missing

Эти ситуации необходимо различать.

| Ситуация | Проектное поведение Horizon |
|---|---|
| Числовой ID присутствует в чанке, но имени нет в реестре | Unknown; исходные id/meta сохраняются |
| Имя есть в реестре мира, но реализация блока отсутствует | Missing; исходное имя и ID сохраняются |
| Мод снова доступен | Имя может быть связано с реализацией после проверки совместимости |
| Сохранение неизменённых данных | Unknown/missing не заменяются молча на воздух |

Для неизвестного ID модель использует служебное имя:

```text
horizon:unknown_<id>
```

Это внутреннее обозначение Horizon.
Оно не должно подменять исходную запись FML в сохранении.

Политика поведения placeholder в текущем контракте:

- размещение через обычную игровую механику запрещено;
- при явном разрушении блок может быть удалён;
- неподтверждённый дроп не создаётся.

Эта политика является решением Horizon,
а не результатом проверки поведения Forge.

### Исправление прежнего утверждения о Forge

В прежней версии документа утверждалось,
что Forge освобождает ID отсутствующих объектов.

В просмотренном `GameData.java` ветки FML `1.7.10`
обработка missing mappings вызывает `gameData.block(remap.id)`,
то есть блокирует ID от повторного использования.

Поэтому резервирование ID само по себе нельзя считать
отличием Horizon от FML.

Сохранение исходных имён и содержимого отсутствующих блоков —
отдельное проектное требование Horizon.
Блокировка номера сама по себе не гарантирует сохранение этих данных.

Просмотренная ветка исходников отдельно не привязана
к точной ревизии установленного Forge 10.13.4.1614.
Проверка настоящего мира после удаления мода не выполнялась.

## 6. Граница с внутренними состояниями Horizon

Для legacy-режима Python-модель задаёт отдельную таблицу:

```text
4096 ID × 16 metadata = 65536 состояний
```

Преобразования модели:

```text
state_id = (legacy_id << 4) | metadata
legacy_id = state_id >> 4
metadata = state_id & 15
```

Это выбранная схема legacy-режима.
Её нельзя считать универсальной моделью всех современных
состояний блоков Horizon.

Требования к последующей реализации:

- legacy-данные преобразуются без потери исходных id/meta;
- правила современного реестра не применяются к legacy-миру автоматически;
- реестр конкретного мира определяет смысл числовых ID;
- служебные placeholder не уничтожают исходные данные;
- совместимость с существующими state/palette Horizon
  проверяется при реализации W01/W02.

Python-класс LegacyStateTable проверяет выбранное отображение.
Он не доказывает, что соответствующий Rust-реестр
или контейнер палитры уже реализован.

При 65 536 возможных значениях прямой глобальный индекс требует 16 бит.
Конкретное хранение локальных палитр относится к реализации
и должно проверяться отдельно.

## 7. Граница с предметами

Legacy item ID и legacy block ID не являются взаимозаменяемыми типами.

Нельзя:

- считать любой блок доступным предметом;
- определять ItemBlock только по диапазону ID;
- всегда получать metadata предмета как `damage & 15`;
- считать `item damage` полноценным состоянием блока.

Преобразование ItemStack в размещаемый блок зависит
от конкретного предмета и относится к S08 и поведению блока.

### Семантика item_kind()

После исправления метод возвращает:

| Значение | Условие |
|---|---|
| `free` | Записи с таким ID в таблице предметов нет |
| `item_block` | Предмет и блок имеют одинаковые имя и ID |
| `item` | Есть самостоятельная запись предмета |

Значение `free` не означает,
что ID свободен для новой регистрации.
Он может быть занят блоком или находиться в blocked.

Модель определяет ItemBlock по связи записей реестра;
это не проверка Java-класса настоящего объекта Forge.

## 8. Адаптер modern_view

modern_view() — вспомогательная модель преобразования для отображения.
Она не используется как источник данных для сохранения,
сетевого протокола или игровой логики.

В существующей модели предусмотрены исключения:

- legacy stone не превращается в гранит или диорит
  только из-за ненулевой metadata;
- свободные в ванили 1.7.10 ID 165–169
  не получают автоматически смысл блоков из более поздних версий;
- модовый блок определяется своим именем,
  а не современной трактовкой его числового ID.

Полнота таблицы визуальных преобразований в S02 не подтверждается.
Она требует отдельной проверки в задачах рендера.

| ID 1204 | Blocks 180, Add 4 |
| packed 65535 | ID 4095, meta 15 |

а не результатами установки настоящего мода.

## 10. Мои ручные проверки

Окружение: Minecraft 1.7.10, Forge 10.13.4.1614.
Установка подготовлена в S01.
Пользовательские моды в проверенном мире отсутствуют.

### 10.1. Реестр настоящего мира

Я прочитал раздел FML из level.dat.

Получено:

- всего 486 записей ItemData;
- 171 запись блока с префиксом `\u0001`;
- 315 записей предмета с префиксом `\u0002`;
- ID блоков от 0 до 175 с пропусками 165–169;
- 144 общих ID блока и предмета;
- имена во всех 144 общих парах совпадают.

Примеры записей:

| Имя | Вид | ID |
|---|---|---|
| `minecraft:air` | Блок | 0 |
| `minecraft:stone` | Блок и предмет | 1 |
| `minecraft:wool` | Блок и предмет | 35 |
| `minecraft:double_plant` | Блок и предмет | 175 |

|---|---|

Журнал запуска сообщает версию FML `7.99.40.1614`.
Это отдельное значение из журнала, а не замена значения ModList.

### 10.3. Round-trip настоящего реестра

Я загрузил записи настоящего FML-реестра в LegacyRegistry,
выполнил inject_world() и обратное преобразование to_fml().

Сравнение подтвердило сохранение:

- всех пар имя/ID блоков и предметов;
- множества BlockedItemIds;
- BlockAliases и ItemAliases;
- BlockSubstitutions и ItemSubstitutions;
- ModList.

Неожиданных missing-записей не возникло.

Результат:

```text

```

Это проверка реестра мира без пользовательских модов.
Она не подтверждает сценарий удаления настоящего мода.

### 10.4. Воспроизведение дефекта item_kind()

Я зарегистрировал в Python-модели блок
с параметром item_block=False.

До исправления получил:

```text
block_id=0
item_registered=False
item_kind=item_block
FAIL: reports ItemBlock without an item entry
```

Причина: метод учитывал наличие блока
без проверки соответствующей записи предмета.

Я изменил метод так, чтобы он сначала находил запись предмета,
а затем проверял совпадение имени и ID с блоком.

Добавлены три регрессионных теста:

- блок без предмета;
- блок с соответствующим ItemBlock;
- самостоятельный предмет.

Первый тест также проверяет,
что ID блока без предмета не выдаётся другому предмету.
